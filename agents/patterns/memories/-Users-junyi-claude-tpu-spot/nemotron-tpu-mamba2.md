Final bug was a TP sharding scramble: feeding concatenated `[x|B|C]` (logical dim 6144) to `shard_map P(ATTN_HEAD)` split it into contiguous chunks crossing the x/B/C boundaries → each shard's x-heads and B/C-groups didn't correspond → SSD multiplied mismatched x⊗B → garbage. FIX in `mamba2_tpu_patch.py`: split x/B/C (and conv weight/bias) as SEPARATE shard_map args using a FRACTION of each tensor's own dim (`n1=d*inter//conv_dim`, robust to logical-6144 vs per-shard-1536), re-concat per-shard inside `_run_local`. Per-shard invariant after fix: x/B/C all shard r→HF quarter r cos=1.0. (Localized via HF CPU reference + per-shard post-conv dump; earlier false leads came from comparing decode-step dumps to HF prefill — dumps must be prefill-only/save-once.) jagged-mamba2 chunked kernel NOW wired into prefill (`mamba2_tpu_patch.py` + `mamba2_prefill_jagged.py`, env `MAMBA_JAGGED=1`): `lax.cond` routes pure fresh prefill → jagged kernel, else token-scan; jagged emits y, final ssm_state computed by closed-form `state_s=Σ_t exp(cumA_last−cumA_t)·dt_t·(x_t⊗B_t)` and scattered to cache. Validated: y+state cos=1.0 vs token-scan; end-to-end output identical (Paris). **Benchmark**: isolated SSD jagged is 6–27× faster (e.g. 64-seq T=19120 workload: token-scan 235ms vs jagged 8.8ms = 26.7× per-shard H=16). BUT end-to-end prefill barely moves at moderate scale (~520 tok: ~0%; 48-seq ~4500 tok: ~7%) — under enforce_eager the SSD is only ~4% of prefill, dominated by MoE/attention/per-layer dispatch. Win materializes at large batch/long seq or in compiled mode. Default stays token-scan (robust, all paths); jagged opt-in via env. Caveat: per-shard H=16 pads to kernel's hardcoded H=128 (8× waste) — specialize kernel to H=16 to improve. Full write-up: `nemotron/REPORT.md`.

**Open bug (localized to SSD output `ssm_out` in layer-0 mamba)**: HF CPU reference (transformers 5.5.3, gives correct " Paris") vs TPU, layer-0 mamba internals, PREFILL (5 tokens). CRITICAL: dumps must be PREFILL-only — callbacks fire every forward and overwrite, so without a save-once guard you compare the last DECODE step (1 tok + padding) to HF prefill → bogus (this caused a false "layer-0 breakpoint" earlier). With save-once (`LAYER0_DBG`, skip if file exists): **in_proj_in, gate, x, B, C, dt (pre-conv) all cos=1.0** (in_proj weight load + `[gate|x|B|C|dt]` split CORRECT), but **`ssm_out` cos=0.0157, 2.6× too large** → the SSD output is wrong; norm_out/out follow. MAMBA_DBG3/CONV_DBG only validated SSD/conv vs MY OWN refs (same formula), NOT vs HF — so a conv-vs-HF or SSD-formula/layout-vs-HF difference is the remaining suspect. NEXT: compare post-conv x/B TPU vs HF (`PCONV_DBG`→/tmp/tpu_pc_*.npy; HF hf_layer0.py→/tmp/hf_pc.npz). post-conv matches HF → SSD bug (token-scan vs HF chunked, or A/D/dt_bias sharding); post-conv differs → conv-vs-HF (state-zeroing/has_initial_state, weight, silu). **ROOT CAUSE FOUND**: TP sharding scrambles x-heads vs B/C-groups. Per-shard post-conv dump shows conv VALUES correct (every shard matches some HF quarter cos=1.0) but shard→head mapping is scrambled AND inconsistent between x and B (x shard2=HF-q3, B shard2=HF-q0) → within a shard x-heads and B/C-groups don't correspond → SSD multiplies mismatched x⊗B → garbage. Reason: `mixed_xBC` per-shard is `[x_r|B_r|C_r]` (x head-sharded, B/C group-sharded — disjoint per-rank ranges, NOT one uniform P(ATTN_HEAD)); feeding the concatenation to shard_map re-splits the logical `[x_full|B_full|C_full]` into contiguous chunks crossing x/B/C boundaries. `reorder_concatenated_tensor_for_sharding` did NOT fix it. **FIX (next session, in `nemotron/mamba2_tpu_patch.py`)**: split x/B/C as SEPARATE shard_map args (each contiguously shardable), split conv weight likewise, conv each / re-concat per-shard inside `_run_local`, then SSD. Per-shard slices already correct, so this preserves them. This is the LAST known bug — in_proj/split/conv-values/SSD-math all validated. Diagnostic scripts in repo `nemotron/debug/`.
