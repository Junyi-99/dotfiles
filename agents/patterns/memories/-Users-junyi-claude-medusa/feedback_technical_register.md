在所有技术场景下使用专业书面表达,避免口语化措辞。

具体禁忌(用户明确点过的反例):

- "走 X" → 应为"在 X 层对应/lower 为/经过 X 路径"
- "做 X" → 应为"执行 X / 实施 X"
- "包了一层" → "封装"
- "套路类似" → "实现路线类似"
- "可以做 / 写起来不难 / 几乎肯定要自己写" → "可实现 / 实现简单 / 需自行实现"
- "漏 fuse / 被打成多 kernel" → "在 fusion 中遗漏 / 被拆分为多个 kernel"
- "严重不 compile-friendly / 正常 generate 不会走" → "编译不友好 / 标准 generate 不经过"
- "把 X 合并 / 当权重 / 投到 Y" → "合并 X / 作为权重 / 投影至 Y"
- "你做的重点 / 你之前做的 / 给你的建议 / 需要我帮你写吗?" → 删除第二人称指代,改用陈述/祈使句
- "trace 注 / 特殊点: / 特殊:" 之类自造标签 → 直接并入正文描述
- "然后 / 几乎 / 基本上 / 大概 / 套路 / 搞" 等口语副词与名词 → 删除或替换为更精确的表达

**Why:** 用户在 Gemma4 算子表(`reborn/ops.md`)review 时明确指出"trace 注"等措辞看不懂、不专业,要求改写并将偏好持久化。技术文档与对话的目标读者(做 Pallas/Ascend kernel 移植的工程师)需要无歧义的描述,口语化表达会增加理解成本并降低文档权威性。

**How to apply:**
- 输出技术分析、代码 review、文档撰写、问题汇报时,默认采用书面专业语体
- 写完后扫一遍是否有"你/走/做的/然后/可以做/写起来/包了一层"等关键词,有则改写
- 涉及 aten/HLO/IR 等编译器层级时,使用"在 X 层对应 / lower 为"而非"走 X"
- 不使用自造的中英混合标签(如"trace 注:")作为段内引导词,改为整句描述
- 非技术性的闲聊场景不强制此规则,但仍避免空泛修饰词(参见 CLAUDE.md "Writing Constraints")
