## 1. PR 发布前按目标 base 核对范围，并重新检查生成物

**触发场景**：从已有开发分支拆出独立改动、修改 PR base、向另一个仓库贡献，或用户质疑文件数/混入无关内容。

**可复用步骤**：
1. 明确目标仓库、真实远端 base、应包含的功能及排除项；不能只依据本地 main 或旧 PR base。
2. 同时审查相对目标 base 的提交列表、文件列表和实际 diff；改变 base 后重新计算。
3. 若任务建立在未合并工作上，从干净远端 base 建分支，移植目标提交并逐块解决依赖，避免把整个旧分支带入。
4. 运行构建/端到端测试后再次检查工作区和最终 diff；识别测试修改的示例、自动生成的本地化文件等。
5. PR body 只描述最终改动和验证；切换目标仓库时检查旧 issue/PR 编号与链接是否仍正确，验证发布后的文件数与提交数。

**原始证据**（统一绝对日志路径：`/Users/junyi/.claude/projects/-Users-junyi-claude-skim-cc/3f526968-92eb-4957-ab87-81557824f215.jsonl`）：
- 第 1648 行：“base 改到 main”；第 1669 行助手说明更换 base 后出现 PR #1 的 11 个提交，显示 28 个文件。
- 第 1673 行：“不要提交 examples/demo-paper 的更改”；第 1726 行：“不要把 pr1 的内容引入进来。”第 1731 行随后从远端 main 建新分支 cherry-pick。
- 第 1901 行：“为什么 file change 是 24”；第 1936 行助手承认构建自动重写的 `Localizable.strings` 被 `git commit -am` 带入，删除后 23 个文件。
- 第 1939 行用户要求移除 PR body 的会话链接并贡献上游；第 1976 行助手报告还清理了在新仓库含义不同的旧 PR 编号引用。

**频率/信心**：1 session，1 次功能拆分与发布链；其中至少 3 类具体污染问题（其他 PR 历史、示例文件、生成本地化文件）。这些是同一工作链上的返工，不能写成 3 次独立成功复用。对方法必要性的信心高，对跨项目频率的信心低。

**建议 skill description**：在拆分分支、修改 PR base 或贡献上游时，核对目标 base 下的提交和 diff，剔除无关历史与构建/测试产物，并校正 PR 说明和仓库引用。

**边界及反证**：不是“每次修改都必须重写历史”；有意 stacked PR 可以保留依赖，但必须符合用户意图。本例最初仅改 base、随后告知混入内容，未满足最终独立接口 PR 的需求，属于失败教训。删除会话链接本身是用户偏好，不应单独生成一个 skill。

## 2. 用实际渲染闭环验证原生界面布局（候选）

**触发场景**：原生桌面窗口出现工具栏溢出、空白、文字重叠；代码和编译结果不足以判断布局。

**可复用步骤**：复现窗口与显示条件；检查系统控件风格和布局约束；为难以直接截图的视图建立最小离屏窗口并渲染 PNG；按真实列宽验证换行、合并网格单元格与 fitting size；在最终应用里再次打开相应窗口确认。

**原始证据**：同一绝对日志路径第 243 行：“claude 这个 tab 是折叠起来的”；第 322 行：“为什么这么多空行”；第 355 行：“文字叠在一起了。”第 379 行助手明确提出把 preferences 实现编译进小 harness，“离屏渲染成 PNG 看实际效果”；第 380 行工具调用构造 NSApplication、NSWindow 和真实 preferences view。第 896、1592 行分别再次要求“构建，跑起来我看看”“编译并运行。我看看”。

**频率/信心**：1 session，3 个连续布局反馈，至少 1 个具体离屏 harness 实施证据；两次后续运行请求是不同阶段验收，不能算两个独立布局工作流。方法信心中，泛化频率低。

**建议 skill description**：排查 AppKit 布局溢出、空白或重叠时，结合原生控件约束检查、最小视图离屏渲染和最终应用验收，确认实际视觉结果。

**边界及反证**：编译通过不能证明视觉正确；本例早期修复后用户继续报告重叠，正说明缺少视觉验证的风险。仅针对有真实布局症状的原生应用；不要把本项目的窗口尺寸或 NSGridView 特例当通用规范。证据不足以说明应该另建独立 skill，可纳入已有 UI 调试 skill。

## 3. 沿越界访问清单收敛应用集成接口（候选）

**触发场景**：两个组件通过脚本/CLI 集成，但调用方仍直接读对方存储文件、拼路径、解释内部状态或复制标记规则。

**可复用步骤**：先画组件与宿主边界；列出双向读写通道；检索路径、状态判断、标记字面量等泄漏点；定义少量调用方实际需要的稳定查询/命令；由一侧提供版本化数据，由另一侧桥接统一访问；逐点迁移并补接口测试与边界文档；检查旧直读路径并做端到端验证。

**原始证据**：同一绝对日志路径第 1103 行：“现在 skimcc 和 skim 之间有一个抽象层吗”；第 1131 行请求 Mermaid，第 1137 行要求把 CLI 与构建工具归入 host；第 1143 行明确：“所有在 skim 和 skimcc 之间的操作，都经过一个中间层进行隔离”。第 1171 行工具调用检索 ledger 文件路径、评论 ID 和 `cc:` 前缀泄漏点。第 1644 行助手把改动归为新接口、卡片控制器、零碎越界、文档四类，解释部分文件只是将标记字面量换成 bridge 方法。

**频率/信心**：1 session、1 次明确接口隔离重构；前面的多次架构提问是同一问题的澄清。候选，方法信心中，未证明值得单独安装成 skill。

**建议 skill description**：在跨组件集成中发现调用方直接依赖对方存储或内部状态时，盘点越界访问，定义稳定查询接口，通过桥接层迁移并验证兼容性。

**边界及反证**：不应把所有文件访问一律包一层；先确认组件所有权和解耦收益。此次用户主动选择中间层，不证明所有项目都需要相同架构。也不能把具体 `locate/view` 命令或该项目目录规则持久化成通用方法。
